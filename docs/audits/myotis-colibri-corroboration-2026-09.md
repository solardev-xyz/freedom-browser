# Colibri as corroboration for stale-anchor Myotis

**Implementation follow-up:** the subsequent [recovery spike](evidence/myotis-recovery-spike-2026-09/README.md) demonstrated live Myotis bootstrap, finalized advancement, restart, and exact independent Colibri state matches on Ethereum and Gnosis. The original research below predates those native runs; its statements about live recovery being untested describe that earlier scope. Shipping behavior remains unchanged.

**Colibri is a viable component on both Ethereum and Gnosis, but our current Colibri configuration is not a drop-in answer to stale-anchor recovery.** We successfully verified public block proofs on both chains using Freedom’s exact package. Colibri can obtain independent checkpoint evidence, and its verified block proofs contain beacon headers from which comparison roots can be derived. However, ordinary Colibri success does not guarantee independent evidence, and a single matching finalized root cannot safely authorize every subsequent Myotis result.

The strongest next design is **an explicitly authenticated, fresh checkpoint followed by a clean Myotis bootstrap**, or an ongoing verification policy that binds every released result to independently corroborated state. Colibri can help supply that evidence. If its checkpoint provider is ultimately the source we trust, fetching that provider’s checkpoint directly may be simpler than running a second verifier just to inherit the same trust.

This is a research conclusion, not an implementation change. The PR remains draft and retains its explicit-consent behavior.

The WASM SHA-256 is `7bd999c2183d9863c0b791e3cdefd8f5b2bc7e095760a30436660d58c1f6ea3f`. Release-source provenance is established; this was not a reproducible-build audit of the WASM artifact. ### 1. Where Colibri’s trust actually comes from

Freedom constructs Colibri with `Strategy.VerifiedOnly`, normally enables `zk_proof`, and does not configure checkpoint witness keys or a custom checkpoint policy. Both chains have a configured prover. [Freedom client configuration](https://github.com/solardev-xyz/freedom-browser/blob/5fcc002415a559c4474c90ce8710ad0b92d01831/src/main/ens/colibri-resolver.js#L195), [endpoint configuration](https://github.com/solardev-xyz/freedom-browser/blob/5fcc002415a559c4474c90ce8710ad0b92d01831/src/shared/endpoint-sources.json#L1)

Colibri has three relevant routes:

| Route                            | What establishes the starting trust                                                                                                                                                                                                                             |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Non-ZK, cold state**           | Obtain a finalized root from a checkpoint/Beacon API, then verify the bootstrap header and committee Merkle branch against that trusted root. The endpoint’s claim that this is the canonical finalized root is the external trust input.                       |
| **ZK, no configured witnesses**  | Verify committee transitions from a fixed chain-specific root. When its period-gap policy calls for an external check, a modern checkpoint proof binds the resulting committee to a checkpoint header and compares that header’s root with an external service. |
| **ZK with configured witnesses** | Verify checkpoint signatures from the configured addresses, header linkage and the ZK proof. The inspected implementation requires **all configured signers**, not an arbitrary majority threshold. Freedom currently configures none.                          |

Sources: [cold checkpoint fetch/bootstrap](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/sync_committee_state.c#L231-L365), [ZK/anchor branch selection](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/sync_committee.c#L406-L468), [committee-to-checkpoint binding](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/sync_committee.c#L75-L132), [witness verification](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/sync_committee.c#L206-L258).

**The ZK proof alone does not resolve weak subjectivity.** It proves the encoded transition checks were satisfied; it cannot distinguish a canonical history from a historical-key forgery that satisfies those checks. The additional useful trust comes from the checkpoint service or witness operators. A second implementation adds software diversity, but is not automatically a second independent canonical-chain observation. The [Ethereum light-client specification](https://github.com/ethereum/consensus-specs/blob/master/specs/altair/light-client/light-client.md#light-client-sync-process) likewise begins with an out-of-band trusted block root.

### 2. Why the existing defaults are insufficient for an independence guarantee

**Checkpoint URLs are sequential fallback, not a quorum.** Colibri combines `checkpointz`, `beacon_apis`, and `prover` URLs, returning the first successful HTTP response. Mainnet lists several dedicated checkpoint services; Gnosis lists `checkpoint.gnosischain.com` first. If independent services fail, the list can reach a Colibri consensus endpoint or the prover itself. Two different URLs are not necessarily two operators. [Chain defaults](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/bindings/emscripten/src/chains.ts#L36-L95), [fallback routing](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/bindings/emscripten/src/http.ts#L177-L215), [first-success loop](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/bindings/emscripten/src/http.ts#L44-L91).

An offline test of the installed JS confirmed this: simulated failures of the dedicated checkpoint and beacon endpoints were followed by successful acceptance of the configured prover’s root response. This establishes fallback behavior, not a cryptographic exploit. A dedicated corroboration path must restrict allowed source identities and record which source actually supplied the evidence; merely setting a `checkpointz` list does not exclude the appended fallbacks.

**ZK selection is not invariant.** On certain errors containing `zk sync proof`, the JS client switches `zk_proof` off and retries. This is another verification path, not inherently an unverified RPC fallback, but any promised witness/checkpoint policy must survive that transition. [Automatic retry](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/bindings/emscripten/src/index.ts#L329-L349).

**A warm-cache success need not contact an independent source again.** The relevant WSP logic compares committee-period gaps, rather than requiring a new external observation on every request. We therefore cannot use the presence of a recent-looking block or a successful proof as proof that a fresh independent checkpoint check happened during this recovery. [Gap policy](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/sync_committee.c#L265-L282).

Configured witness keys offer another route, but we have not established an available, independently operated signer set for either chain. The reference signer is designed to check a checkpoint against its own Beacon API before signing, so its upstream and administration are part of the trust model too. [Signer protocol and checks](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/cp_signer/README.md).

### 3. Can the two clients expose something meaningful to compare?

**Yes. Myotis already exposes `finalizedRootHex` and `finalizedSlot` through `statusJson`.** The root is a beacon-header SSZ root, not an execution block hash. Freedom’s current status allowlist drops both fields. Preserving and validating them is a Freedom change; it does not require a new native export. [Myotis serialization](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-engine/src/host.rs#L1780), [Freedom allowlist](https://github.com/solardev-xyz/freedom-browser/blob/5fcc002415a559c4474c90ce8710ad0b92d01831/src/main/myotis/myotis-process.js#L34).

Colibri’s verified full-block proof contains the beacon header. We successfully decoded the captured proofs on both chains and computed its SSZ root. A prototype can fetch a proof for the explicit execution height associated with Myotis’s finalized header, verify those exact bytes, then compare **chain, slot and beacon root**. It must also check the requested/returned execution height and evidence age. Do not decode one response and verify another. [Proof APIs](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/bindings/emscripten/src/index.ts#L211), [block verifier](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/verify_block.c#L190).

Two qualifications:

- Myotis’s status combines consensus and execution observations that are not an atomic tuple. A sync transition can mix observations. A prototype must retry unstable snapshots, but repeated matching polls are only a heuristic. A robust gate needs cryptographic tuple binding and preferably an upstream atomic finalized tuple. A race or different head height must not be called an attack. [Status assembly](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-engine/src/host.rs#L445-L517)
- Colibri’s ordinary RPC result does not expose all verified proof metadata/provenance. A clean integration should expose that metadata through an explicit helper/API rather than depend on incidental network interception.

There is also a possible shortcut through the next execution block’s verified `parentBeaconBlockRoot`, but this needs separate qualification for skipped slots, proof modes and status consistency. It is not the recommended initial security boundary.

### 4. “Finalized” is not established merely by the RPC tag

The live Ethereum prover rejected `eth_getBlockByNumber("finalized", false)` and `eth_getBlockHeader("finalized")` with HTTP 502 / `Invalid block: "finalized"`.

Separately, the verifier treats `latest`, `safe`, and `finalized` as wildcard block-number matches in this proof path. In an offline test, the same captured **latest** proof verified when the request tag was changed to **finalized**, on both chains, without adding finality evidence. Therefore the RPC tag is not a finality certificate. [Tag matching](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/verify_block.c#L124-L145), [beacon-header verification](https://github.com/corpus-core/colibri-stateless/blob/2fae243d57cc67cef1ba7ee2bef8390fcd22efd0/src/chains/eth/verifier/beacon_header.c#L94).

For the proposed design, use explicit positions and obtain finality evidence from an authenticated finalized checkpoint or a verification path that actually proves finality. Matching two `latest` values, matching balances, or matching block numbers is insufficient.

### 5. One successful comparison is not a permanent release of the stale run

This is the most important architectural finding. Matching an independently authenticated **finalized** checkpoint root establishes agreement on that checkpoint. It does **not** by itself authenticate Myotis’s in-memory current/next committees or its later optimistic state.

A threat-model construction is an attacker-controlled committee lineage that references a genuine finalized header inside an invented signed attested state while retaining attacker-selected future committees. A finality branch proves inclusion in the signed state; it does not make that invented state canonical. That construction was not demonstrated as a production exploit in this research. It explains why “one good hash, then trust the node forever” is an inadequate security argument. [Myotis update processing](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-consensus/src/store.rs#L210-L305).

Even without that construction, a finalized checkpoint F says nothing about an uncorroborated optimistic read at H above F. Current Myotis generic calls do not provide the exact execution-root provenance needed for a robust per-result policy; the engine ignores the supplied block selector in this call path. [Call implementation](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-engine/src/host.rs#L774), [Freedom trust labeling](https://github.com/solardev-xyz/freedom-browser/blob/5fcc002415a559c4474c90ce8710ad0b92d01831/src/main/networks/chain-data-router.js#L662).

Two defensible designs follow:

1. **Authenticate a recent checkpoint and bootstrap a clean Myotis store against it.** Verify committee membership against that checkpoint’s state root and discard untrusted future state. Current Node v0.1.9 accepts only the network/data directory at creation and does not expose checkpoint import/rebootstrap. This needs an upstream API change, plus safe snapshot handling. Do not write internal snapshot files as an unofficial API. [Node creation API](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-node/src/lib.rs), [fixed network configuration](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-engine/src/host.rs)
2. **Keep an ongoing gate on results.** Release only reads whose exact block/state is independently corroborated. That requires complete result provenance, generation/cache invalidation and coverage of every consumer. A one-time UI readiness change is insufficient. This is a larger integration than simply comparing one root.

### 7. Alternative sources and practical recommendation

| Source                                              | Value                                                                  | Remaining trust/engineering requirement                                                                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Explicitly trusted Beacon API / checkpoint service  | Direct fresh canonical-finalized checkpoint                            | Trust the chosen operator and HTTPS identity; enforce age, chain and rollback policy.                                                                              |
| Multiple independently operated checkpoint services | Corroborated canonical observation                                     | Establish actual operator independence; compare the same checkpoint/ancestry, not unrelated latest heads; define quorum and failure behavior.                      |
| Colibri with a dedicated source/witness policy      | Proof-backed result plus checkpoint evidence; implementation diversity | Prevent fallback to the proof operator, expose provenance and finality, qualify every allowed bootstrap path.                                                      |
| Signed checkpoints over Swarm                       | Distribution independent of Freedom releases                           | Authenticate publishers, expiry, chain and rollback; plan rotation/revocation and retrieval before Myotis is ready. Swarm supplies transport, not canonical truth. |
| Pinned beacon peers / diverse peer Status           | Additional network observations                                        | Authenticated operator identities can help; arbitrary discovered peers are Sybilable and Status claims are not finality proofs.                                    |
| Execution-layer peers                               | Evidence that other nodes know the execution header                    | Helpful additional signal; knowing a hash does not authenticate consensus committees or establish finality.                                                        |
| User’s own continuously synced full node            | Clear user-selected checkpoint authority                               | Useful advanced option, not an assumption for ordinary installations.                                                                                              |

**Recommendation:** pursue the fresh authenticated checkpoint + clean bootstrap API first, with an explicit per-chain source policy. Colibri is a useful candidate for obtaining or checking evidence, but do not make an ordinary Colibri request’s success the permanent stale-anchor override. The same checkpoint policy can later be distributed through Swarm; corroboration and checkpoint refresh share the core trust decision.

If we prototype option 3 first, keep it as private catch-up with a real gate on consumed data, explicit source separation, comparable root/slot checks and bounded retries. State exactly which additional operator an attacker would need to compromise. Different library names, IPs or domains are not an adequate independence claim.

### 8. Failure behavior and remaining qualification

- **Different heights or transient mixed status:** normalize/retry; not a conflict.
- **Timeout, unavailable source, stale evidence or unsupported prover method:** unconfirmed; keep the gate closed, then communicate recovery status. Do not silently turn this into option 2.
- **Invalid proof:** reject that evidence and try another allowed source. This alone does not prove two valid conflicting chains.
- **Authenticated, comparable finalized histories conflict:** stop trusting the affected state, retain evidence and require recovery.
- **Node restart, policy change, generation change or expired evidence:** invalidate the gate and cached authorization.

Before shipping, qualify actual stale-anchor Myotis catch-up and result binding on both chains, period boundaries, skipped slots, conflicting histories, warm/stale caches, late responses, restart races and every fallback/ENS/wallet read path. An end-to-end happy-path equality test would not replace the adversarial state-binding tests.

Source review also identified legacy proof-format, committee-period binding and cache-transition questions that need targeted upstream tests/clarification before making a strong historical-key-attack resistance claim. They remain unconfirmed security hypotheses, not reported here as established exploits. Modern-format happy-path success does not establish safety of every format/path a verifier accepts.

**Independent review:** three local source/threat/API reviews, a separate Claude review, and the Linux probe informed this synthesis. Claude independently emphasized committee-state binding, the need to avoid a one-time finalized-root approval, and the persistence consequence below. Reviewer suggestions were checked against source and experiments; speculative attack constructions are distinguished from executed tests.

**Consent persistence matters:** the native acceptance flag is not saved, but chain state acquired during an accepted run can be saved and selected as the newer anchor on restart. If still fresh, that state may avoid another stale-anchor prompt. Stopping a handle therefore does not undo the trust effect of the previous run. A quarantine policy should keep uncorroborated state separate and promote it only after authenticating the state needed for future verification. Merely renaming a directory after one hash match would not solve committee binding. [Snapshot selection](https://github.com/biafra23/myotis/blob/b3c1fd0ff2ebd6c1df593fca40a46c22fa506f4e/rust/myotis-net/src/sync.rs#L1676-L1760).

The most useful upstream questions are: can Myotis expose an atomic authenticated state/committee tuple and accept a caller-supplied recent checkpoint for clean bootstrap; can Colibri expose verified beacon metadata and the actual bootstrap/source provenance; and can every permitted Colibri proof format/cache transition be regression-tested for committee/period/checkpoint binding? No upstream issue or message was posted as part of this research.

**Decision for this PR:** keep the current draft unshipped while choosing the trust policy. Colibri is technically capable enough to justify a prototype on both chains; the current defaults plus a one-time hash comparison are not sufficient to justify silent automatic recovery.
