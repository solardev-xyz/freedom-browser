## Shape and authority

The structural parser already accepts exactly three disjoint shapes (`railgun-poi-payload.js`):

| Authenticated operation | Capsule | Blinded outputs           | Marker                           |
| ----------------------- | ------- | ------------------------- | -------------------------------- |
| Private transfer        | v1      | exactly one               | exact `0x00`                     |
| Full unshield           | v1      | zero                      | exact 32-byte own Railgun TXID T |
| Partial unshield        | v2      | exactly one change output | exact 32-byte own Railgun TXID T |

For nonzero T, retain all leading zero bytes. Do not turn T into a shortened integer or hash it again. Empty outputs plus zero marker remains invalid. Payload shape identifies a structural category, never ownership, history, eligibility, genuine proof authority or consent.

`railgun-own-poi-proof-data.js:35–105` already binds partial capsule v2, exact ordered `[changeCommitment, unshieldCommitment]`, actual TXID witness root/index/T and one output. `railgun-poi-verify-job.js:43` already requires POI verification-key `nPublic === 8`. Reconstruction/witness supports one ordinary change NPK/value and the final unshield commitment in the transaction binding. Reuse this; there is one combined POI_3x3 proof, not separate change and unshield proofs.

Every genuine binder must first compare the derived shape/count/zero-versus-nonzero marker category against authenticated capture, and compare the exact marker T once the genuine own-TXID derivation/witness is available, while retaining account/public identity, selector, source checkpoint, creator, index and root joins. An early nonzero check does not establish the exact T and must never be described as doing so. Stored capsule digest alone cannot authenticate an operation-kind claim on a record. Genuine proof history on prepare and genuine operation recovery on later consumers supply those bindings.

## Shared pure shape and selector-domain helper

Proposed location: `src/main/wallet/railgun-own-poi-shape-data.js`, beside the existing pure own-POI input/data normalizers. It must depend only on pure capsule/payload normalization and assertions; no enrollment, registry, privacy context, filesystem, process, time, callback or network imports. The existing `railgun-own-poi-binding.js` keeps its separate strict/stable capture comparison responsibility.

Concrete fixed API:

- `getRailgunOwnPoiShape(capsule)` normalizes the capsule with `normalizeRailgunPrivateCapsule`, accepts only the three exact version/kind pairs, and returns a frozen plain object with exactly `{ kind, capsuleVersion, outputCount, hasPrivateOutput, hasUnshield, selectorDomain }`. `kind` is the existing full operation-kind string; booleans/count follow the table above. `selectorDomain` is the exact existing `freedom:railgun:own-selector-v1\0` or `freedom:railgun:own-selector-v2\0` string (terminal NUL, not a literal backslash). It contains no TXID, marker, digest, proof, freshness or authority flag.
- `assertRailgunOwnPoiPayloadShape(payload, capsule)` uses the same derivation plus `normalizeRailgunPoiPayload`, checks exact output count and marker category (transfer exact `0x00`; either unshield a canonical nonzero 32-byte field), and returns nothing. It deliberately does **not** check the actual T. Do not accept a caller-provided precomputed shape or `partial` switch in lieu of the capsule.

These helpers establish structural consistency even when given an untrusted capsule; they cannot authenticate that capsule. Genuine hosts call them on the normalized capsule obtained from their existing authenticated capture/receipt. The store's document decoder has no capsule and therefore continues to enforce only version-specific structural payload rules; it must not reconstruct an authority claim from marker/count.

Use this one mapping in own-witness/membership/proof and proof-data, prepared **and** attempted output recovery (including its data/worker expectations), cold validation, disclosure planning and fixed sender. In particular, worker admission uses `hasPrivateOutput`, while marker expectations use `hasUnshield`; partial must not fall through the full-unshield keyless branch. Disclosure derives its user-facing operation enum locally from this fixed kind, not from a caller flag or payload alone.

At early plan/store/selector entry, only shape/category can be checked. Once the existing genuine selector or normalized verified own-TXID witness has derived T, each host performs its existing exact marker join: transfer `0x00`, otherwise `'0x' + T`, retaining all 32 bytes. `expectedRailgunOwnPoiFields` and `bindRailgunOwnPoiPayload` retain their exact-root/index/T comparisons; the helper does not replace them. Output recovery compares the worker's recovered change and marker against both the saved payload and the host's fresh expected T. No new exact-T claim is made before that data exists.

Cold validation uses `shape.selectorDomain` when recomputing the actual transaction digest. The existing low-level own-selector producer derives its domain from the independently extracted proved-transaction kind and does not take a capsule; leave that contract intact. Add golden parity tests proving its v1/v2 domains agree with this capsule-based helper after the authenticated capsule/transaction join. A disagreement must refuse, never coerce domains or manufacture a capsule. Shared helper tests cover both forbidden version/kind pairings and malformed/zero/leading-zero marker boundaries; use guard-removal tests at the **exact-T host joins** as well, since category tests cannot detect a different nonzero T.

## Document v3, sequence, floor and immutable attempts

Keep record key `railgun-poi-intents-v1`, file namespace, profile inventory and floor. Version 3 is an explicit older-reader refusal marker for a store capable of combined records, not a new authority field.

- New empty and legacy prepared-only documents remain v1. First legacy attempt changes v1 to v2 as today. Legacy writes to v2 remain v2.
- First successful combined prepare changes v1/v2 to v3 **inside that same prepare commit** with exactly its normal sequence +1. No preliminary migration write, extra sequence or floor increment.
- Once v3, all later writes/reopens retain v3, including attempts of legacy records. Legacy entries, revisions, payloads, input hashes and existing attempted envelopes are not rewritten into a new format.
- `record(value, version=2)` currently allows attempted only when `version === 2` (`intent-store:112`); accept attempted in explicit v2/v3, while v1 still forbids it. Decode only explicit versions1/2/3. Mixed payloads remain forbidden in v1/v2 and allowed structurally only in v3.
- **Critical downgrade seam:** beginAttempt currently calls record without a version and hardcodes next.version=2 (`intent-store:539–546`). Compute target version monotonically (`current.version === 1 ? 2 : current.version`), pass it to record, and retain it in next. Otherwise even attempting a legacy record in a mixed v3 store downgrades the whole document. Remove the default argument from private `record(value, version)` so no call can silently choose version2. Audit **all** call sites: decode at 199 uses the document version; identical prepared comparison at 333 uses current.version (an existing partial record necessarily resides in v3); new/revised prepared construction at 345 uses the explicitly computed target version; beginAttempt baseline at 493 uses current.version; attempted construction at 539 uses the monotone attempt target version. Encode re-decodes under next.version. An identical partial reprepare must return the old record in v3 without sequence/floor/ciphertext writes; it must not accidentally reject through a version2 default or trigger another migration.
- Keep the same exact sequence invariant `sum(revision + attemptedTransition)`, record limit32, sequence ceiling128, revisions<=4 and reserves prepared3/attempted2. Migration consumes no independent transition. Validate existing records under target capacity rules before committing; do not silently raise byte caps to fit combined data. The existing maximum-attempt envelope reserve should be tested at actual mixed boundaries.
- beginAttempt still allocates requestId=attemptedAt exactly once, compares the entire detached prepared baseline under exclusive CAS, writes one immutable attempted entry, advances the floor and readbacks. No retry/reprepare/reset of attempted capsules, including identical payload. Same-nullifier collisions across legacy and partial remain conflicts.
- Preserve strict precommit capture and stable postcommit capture semantics. Archive representation evolution after commit may succeed only when stable fields match; stable drift, floor/readback failure or lost completion after possible commit remains recovery-required and never authorizes a POST.
- Existing ciphertext/floor crash limit remains: rename and floor are not atomic. Before floor repair an old prepared ciphertext can still replay after a failed floor write. Version3 is not additional rollback protection. Test/report the existing before-floor/after-floor distinction.
- Successful current-reader reopen renews a lease and may legitimately write encrypted bytes/floor housekeeping. Preserve canonical entry/envelope bytes across it; do not claim whole-file immutability on successful reopen. Reads/idempotent no-op and rejected old-reader opens have stricter byte/no-write assertions.
- Run exact pinned previous reader against a v3 store: it must refuse the **whole** store, including legacy entries/recovery, before lease/floor/inventory mutation. Preserve ciphertext, floor and filenames byte-for-byte on that refusal; current reader must then recover the same mixed records. Do not fake an older reader by only changing a version check. When enabled, the repository documentation and required user-visible changelog must explicitly state the downgrade consequence: after first combined prepare, older builds cannot open the entire retained-POI store, including its legacy prepared/attempted entries and legacy recovery. This does not mean unrelated wallet stores have migrated. No downgrade writer, record stripping, fallback to an empty store or migration rollback is permitted.
