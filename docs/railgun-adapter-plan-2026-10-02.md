## Reuse and new work

Freedom already has a restricted Railgun keystore in `src/main/identity/privacy-keys.js`. It uses the `babyjubjub seed` hardened HMAC tree, with golden vectors from the CLI's derivation library. Only spending `m/44'/1984'/0'/0'/i'` and viewing `m/420'/1984'/0'/0'/i'` for the selected index are granted. The private-key derivation helper now also matches three public test vectors from the pinned engine; public-key and signature vectors still require the engine cryptographic closure. Ordinary Ethereum BIP32 derivation is incompatible. Reuse this module only inside the trusted host; do not hand its raw-key `deriveAt` capability to the engine. The new `createRailgunViewingKeystore` grants only the selected viewing-key path; spending-public-key derivation still needs the authenticated engine cryptographic closure. Do not add another seed export or derivation algorithm.

The engine's `HardwareWallet` accepts a shareable viewing key and external signer connector. That offers a way to keep spending material outside the engine, without handing it the root mnemonic. The shareable key still reveals viewing secrets and belongs only in encrypted, account-bound storage. The connector is **not** approval enforcement: it receives a hash/public inputs, not a human-readable transfer. Main must independently bind the inputs, outputs, recipient, fees, chain and bound parameters to an issued operation before signing. A generic hash-signing endpoint would defeat this boundary. Main will derive the spending key for a dedicated signer process running the pinned upstream cryptographic implementation. That process will expose public-key derivation and signing bound to an issued, independently checked operation. The engine receives only the viewing key and spending public key. Freedom will not implement new BLAKE-512 or Poseidon primitives.

`RailgunEngine.initForWallet` accepts database, artifacts, quick-sync and txid-validation callbacks. `loadNetwork` expects ethers-compatible providers, including a polling provider. A provider bridge must use only the granted Kohaku RPC capability; engine defaults, Graph quick-sync, POI endpoints and artifact downloads cannot silently open their own connections. POI services and their trust/availability model need separate qualification. Do not return permissive proof-validation results just to make startup succeed.

The current Kohaku encrypted store is too small for an engine merkle database (4 MiB total, 256 keys). The engine will need an independently bounded encrypted key-value backend, probably using the existing SQLite dependency with encrypted values, account/chain binding and transactional batches. A LevelDOWN-compatible bridge must preserve byte ordering, iterator snapshots and atomic batches, and must fail on corruption or revoked access. It cannot report writes as successful after closure. Backup and crash recovery need qualification before spending.

The engine also uses global contract/configuration state. Start with one engine/account per isolated process and revoke transport, storage and signing on lock/profile change. A reusable adapter should depend on injected host capabilities and a pinned runtime contract, with Freedom's review, vault, IPC and journal policy outside it. Keep files within the existing main-process/tooling responsibilities until a separate repository is deliberately created.

## Bounded acceptance sequence

The initial host RPC bridge is implemented separately in `src/main/networks/railgun-host-provider.js`; it is tested with the application's installed ethers dispatcher. This does not yet establish compatibility with the pinned Railgun polling provider or whole-engine egress isolation.

1. Verify and lock the published engine package and transitive closure in an isolated development fixture. The engine itself is exact-pinned but some transitive dependencies use ranges: after approval, verify the engine tarball against the recorded registry integrity, commit the first scripts-disabled install’s lockfile and use `npm ci --ignore-scripts` thereafter. No Freedom dependency downgrade is needed. Qualify deterministic identity, external signing against public test vectors, encrypted storage restart and lock cancellation before enabling network operations.
2. Exercise the actual engine through a host-only provider bridge. Lock the engine's own ethers `FetchRequest` configuration to deny direct HTTP before engine initialization, disable CCIP reads through its setter, and refuse ENS/avatar/fee-data helpers. Require matching host/bridge lifetimes. Deny raw sends, malformed/mixed batches and late responses; deny global fetch/undici, HTTP(S), sockets and DNS in the engine process as well; verify no direct DNS/socket/HTTP path and no hidden quick-sync/POI fallback. A mocked engine cannot satisfy this gate.
3. Provide current Kohaku `instanceId`, `balance` and `notes` with only qualified capabilities. Test actual current interface compatibility. Do not advertise shield/transfer/unshield until their runtime paths are qualified.
4. Add pinned deployment/artifact/POI inputs, controlled discovery, proving and main-owned transaction binding. Journal public submissions and private uncertainty before handoff. Then qualify shield, transfer, unshield and recovery independently.
5. Extract the adapter after its host/runtime contract is demonstrated. Publishing, production enablement, live funding and UI remain separate steps.

New dependency installation requires user approval under AGENTS.md rule 9, including the isolated fixture. The concrete first proposed dependency is `@railgun-community/engine@9.6.0` and its locked transitive dependencies, installed with lifecycle scripts disabled. Proving dependencies/artifacts will receive a separate pinned review when required. No Railgun dependency has been added or installed by this source-research pass.
