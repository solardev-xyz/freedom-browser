# Railgun engine, encrypted storage and offline qualification

The approved development fixture now executes the published **Railgun engine 9.6.0**, with its own **ethers 6.14.3**, independently of Freedom's application dependency graph. This advances the current Kohaku adapter plan; it is not yet a balance/shield/transfer/unshield plugin or a live Railgun integration.

## Encrypted store and compatibility bridge

`src/main/wallet/railgun-store.js` belongs to main-process persistence. Main chooses the file, storage key, privacy context and compatibility binding. Rows encrypt **both keys and values**, use random opaque row identifiers, and bind their authentication to the profile/private account/deployment/compatibility binding. An encrypted digest authenticates the complete row set at open, detecting removed, added or altered rows. It does not detect rollback of the entire database.

SQLite uses exclusive ownership, FULL synchronization (including `fullfsync` on macOS), secure deletion of freed content and transactional batches. The parent directory is fsynced after creation. Creation is explicit; an existing store is never overwritten, and a missing existing file is refused. Schema and empty manifest initialize in one transaction, and existing databases must have exactly the expected schema. A crash before initialization completes can still leave an unusable fresh file: it is preserved for explicit recovery, not silently reset. Lock contention has a separate busy error. This primitive is **not enrolled in the product profile inventory** and is not yet granted to a production engine process.

The in-memory decrypted state is bounded to 32 MiB and 65,536 entries; keys are at most 4 KiB and values at most 1 MiB. Batch input is bounded before copying. Ciphertext digests are cached, although each write still sorts and hashes the row inventory; realistic scan throughput remains unmeasured. Metadata such as file size, row count and ciphertext length is not hidden. Reads use the authenticated open-time snapshot; this is not continuous detection of external disk modification.

`railgun-leveldown.js` receives only the byte-store capability and the engine's own LevelDOWN classes. It implements real encoding-down serialization, atomic batches and range clearing, ordered/reversed iterators, seek, limits, `getMany`, not-found behavior and asynchronous callbacks. Two copied snapshots are allowed at once, bounding snapshot payload to 64 MiB plus overhead. Larger scan concurrency remains unqualified. A full UTXO tree can exceed this store’s key/byte limits; these bounds are for the initial controlled fixture, not evidence that a full Sepolia replay will fit. Revocation wipes retained buffers, closes storage and refuses queued writes and iterator reads. Every failed batch also closes the store and invokes the required owner failure callback; the qualification owner revokes the whole scope. A storage refusal revokes the owner scope and all later storage access. Binding RPC revocation to the same scope is a product-session requirement and is not shown by this fixture.

The 16 storage tests include wrong-key/account/binding refusal, ciphertext/row-set tampering, all-or-nothing invalid batches, SQLite transaction failure, a child killed during a transaction, independent restoration, payload bounds, lock revocation, rejected schema triggers and incomplete-file refusal.

## Actual-engine checks and lifecycle findings

The harness launches creation, deliberately failed-write, and fresh restoration children. Each passes nine grouped checks (27 grouped checks across three processes): upstream public spending/viewing-key and address vectors; equality between a HardwareWallet built from Freedom-derived product-path keys and the engine mnemonic wallet; signature verification with an altered-message negative control; actual engine database encodings and batches; snapshot/range/seek/clear behavior; HardwareWallet creation or fresh-process restoration; the real engine polling provider and network initialization through controlled host RPC; refusal of unqualified artifacts/quick-sync/validation; and store-failure/lock refusal of queued writes/iterators. The failed-write child supplies a valid put followed by an oversized put; the later restoration child confirms neither the early write nor late writes committed, while earlier valid data survived.

The HardwareWallet receives a public upstream shareable-viewing-key fixture. Its external-signing connector checks the engine's hash/input forwarding and deliberately refuses to sign. The separate cryptographic vector and product-path checks use a public test mnemonic/spending key within the test child. The equivalence check retains an encrypted record of that public mnemonic as test data; this is not a viewing-only process-isolation claim. Batch approval is explicitly refused, and an empty signing session is rejected by the fixture connector’s specific guard. This tests the connector contract, not the future production signer policy. This is **not** a qualified main-to-signer process boundary or reviewed transaction-signing policy.

Each child installs and positively tests **87 direct-egress refusal hooks** before importing the engine, locks that engine's ethers HTTP configuration, and observes **zero direct attempts** in the tested operations. Host responses are synthetic; no live RPC, POI service, relayer, circuit download or transaction is used. Every loaded CommonJS module must resolve inside the authenticated fixture or the explicit host module/dependency allowlist; every dependency edge originating in a fixture module must remain inside the fixture. On this darwin-arm64 host, the loaded native files were `bufferutil` and the host’s `better-sqlite3`; BLAKE/Keccak used their JavaScript fallbacks because their installed prebuilds lack darwin-arm64. Other platforms must separately qualify their native cryptographic paths. This is Node JavaScript API evidence, not OS/native containment or exhaustive SDK coverage. Contract-history scanning, note discovery and spendable balances are unqualified.

One intermediate inventory check refused npm’s nested `.bin` links before engine import; exclusions were narrowed to actual `node_modules` bookkeeping locations. Another intermediate resource assertion observed four timers before the short ethers caches expired; the final check drains those caches before requiring exactly two. These harness corrections are distinct from successful engine qualification.

The first network-enabled invocation completed its checks but failed the parent's 60-second deadline because the child remained alive. Source inspection found that upstream `promiseTimeout` leaves its timer running when the operation succeeds. The pinned `unloadNetwork` also returns when a contract is present; the fixture confirms its UTXO tree remains loaded after unload. The final harness therefore explicitly terminates after capability revocation, database closure, egress checks and stdout flush. After allowing ethers’ 250 ms cache timers to drain, every final child reports exactly two remaining timeouts plus stdio and no unexpected debugger errors. A timer census installed before engine import identifies both as 60,000 ms timers created by `engine/dist/utils/promises.js`. Polling is active when host revocation occurs. The parent validates the exact check list, runtime inventory, source hashes before and after the runs, refusal canaries and exit label. It does not claim natural engine teardown is clean. A product session must revoke main-owned capabilities and supervise process termination instead of trusting SDK unload.

The engine's `Database.put` and `batch` can also return successfully after the database is closed. The bridge refuses late operations while called, but cannot fix a wrapper that never calls it. Main-owned session entry/exit guards remain required before exposing operations. No network is reloaded within a child, and permissive default txid-root validators are never used.

[Machine-readable qualification evidence](https://github.com/solardev-xyz/railgun-kohaku-adapter/blob/377c2a5d1aca18f0ed328dfdda955bd7d1ba271c/docs/freedom-qualification/railgun-engine-runtime-2026-10-02.json) records source hashes, exact runtime inventory, all three process reports, native module paths, timer census and the unsuccessful intermediate attempts.
