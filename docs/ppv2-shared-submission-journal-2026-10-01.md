# PPv2 and ordinary-wallet submission coordination

PPv2's private transaction route already persisted hashes before network handoff, but the ordinary wallet could bypass that journal and choose a nonce from a different RPC. This continuation makes both routes share the existing account journal for enrolled Sepolia accounts. It does not enable PPv2 UI or change other chains' transaction behavior.

## Scope and behavior

Opening a PPv2 session explicitly initializes its encrypted public-submission journal, including when no transaction has been sent yet. First enrollment takes the same profile/address/chain lease as an ordinary Sepolia send. An in-flight phone-wallet send therefore prevents enrollment. Once enrolled, a remote signer that controls its own broadcast is refused; the host cannot journal its nonce and signed hash before that remote handoff.

Ordinary sends never enroll an account. For a profile with no PPv2 inventory or stores, they retain their normal signing and transport path, apart from the Sepolia same-account lease, earlier address lookup and preservation of private-state error codes. A PPv2 profile's inventory must authenticate even when deciding that a particular account is not enrolled: locked profiles require unlocking for Sepolia sends, and corrupt/missing/moved state cannot silently disable the guard. Mainnet and other chains retain their existing concurrency and profile-lifetime behavior. Same-account Sepolia preparations fail immediately when another preparation holds the lease; no hidden queue is introduced.

For an enrolled account, ordinary sends check the journal before fee RPCs or signing. Both private and ordinary routes choose the greater of the pending RPC nonce and one past every recorded or archived nonce. An unresolved record blocks either route. Ordinary sends also check value plus maximum gas cost against the observed balance before signing; this reduces avoidable refusals without treating an RPC estimate as proof of successful execution.

The signed transaction must match the prepared intent. The journal then saves and fsyncs its hash and nonce before a one-use, main-owned broadcast permit is issued. The ordinary chain-data router binds that permit to the exact signed hash, chain and active lifetime. A permit-less direct raw broadcast from an enrolled account is refused. Once bytes have been handed to a provider, the enrolled route tries no second endpoint or source. This is a deliberate delivery policy; identical signed-transaction retransmission is normally idempotent, but this experiment requires explicit reconciliation instead of automatic retry.

Lost responses or wrong returned hashes preserve the attempted record and return `PRIVATE_BROADCAST_UNCERTAIN` with the original transaction hash. A filesystem error after the encrypted record was renamed also carries that hash, even if directory sync or inventory maintenance subsequently failed. When the provider returns the matching hash but the vault locks before its acknowledgment can be recorded, the ordinary result still exposes that acknowledgment for payment history in the same profile. It reports `submissionState: attempted` and `requiresReconciliation: true`; no record is automatically resolved. A profile switch still refuses completion into the new profile.

Wallet identity, journal encryption, leases and permits remain in `src/main/wallet/`. The existing chain-data router enforces the permit at its ordinary raw-broadcast boundary and retains its existing transport choices. A wallet-only gate would leave direct raw-router callers able to bypass the journal, which is why the narrow enforcement is at that boundary. No renderer API, IPC channel or package boundary was added.

## Recovery and limits

This is coordination for enrolled accounts within Freedom, not global nonce consensus. Transactions sent before enrollment, other devices/profiles and remote-wallet operations that time out and later complete are outside the journal. A private RPC can lag those operations. The private route never probes the ordinary RPC to fill that gap, because doing so would reveal private-operation timing through the ordinary network path. Existing consumed-nonce reconciliation remains a recovery mechanism, not proof of the original transaction's success.

Enrollment is persistent; scan-only PPv2 startup also enrolls the public account. There is no automatic unenrollment. Every ordinary journaled send requires explicit reconciliation before the next, and this branch still has no product UI for that flow. A begun transaction that never enters the mempool can leave the account blocked. A reviewed replacement/nonce-consumption procedure and safe-release policy remain separate work; insufficient funds, a timeout or an expired quote does not clear an attempt.

Ordinary records currently carry no PPv2 intent. Archiving accepts only a strict prefix and refuses intent-less history: the first ordinary record therefore blocks archiving every later record, including private ones. An enrolled account consequently has at most 64 live records, minus those already present, for further journaled sends on either route before `PRIVATE_TRANSACTION_LIMIT`. A provenance-aware archival policy is the next technical follow-up; unknown legacy records must remain protected.

The lease and atomic journal updates assume one owning process per profile. The live qualification harness now acquires the same profile lock as the application before identity/runtime/network access and releases it on setup failure or normal exit. Lock compromise stops the harness. Other tools must respect that same ownership rule. No live profile or funded runtime was changed during this work.

## Verification

Regressions cover ordinary/private preparation races, first enrollment during an actual pending phone-wallet send, mainnet same-account concurrency, authenticated enrollment and moved/missing state, unsafe nonce quantities, archival nonce floors, initialization racing an attempt, one-use permits, signing/balance refusals, uncertain ordinary broadcasts across restart, and matching acknowledgments after vault lock. Router tests check no second endpoint/source after an enrolled handoff and no provider access without a permit. Harness tests use real profile locks and stop before any identity or network operation.

The runtime remains the independently qualified `fa71e37d…` development archive. The complete real-SDK suite passed again for these host changes; a previous runtime-build qualification alone is not evidence for the new submission behavior.

First-session enrollment can return `PRIVATE_SEND_IN_PROGRESS`; the partial session is closed and opening can be retried after the ordinary send ends. This refusal does not authorize resubmitting any transaction. Post-rename failures in observation, resolution or acknowledgment may also mean their writes landed; their revision guards still refuse stale retries. Only attempt creation currently adds the potentially durable transaction hash to that write-error result.
