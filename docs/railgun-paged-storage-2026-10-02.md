# Railgun paged storage and Electron tree qualification — October 2, 2026

The development Railgun host can now retain a history larger than the original whole-map database without keeping all plaintext records or copying the entire history for each iterator. The real engine also runs its atomic tree workload through the actual Electron utility supervisor, including lock, interrupted staging, acknowledged commit, and cold restoration. This remains infrastructure: no complete scan, wallet balance, proof, signing permission or live Railgun transaction is established.

The implementation stays in `src/main/wallet/`, under the host's existing persistence responsibility. The engine child receives bounded database commands; it receives neither a database path nor the storage encryption key. `storage.format: 'paged-v2'` explicitly selects the new development format. Existing stores retain their original format; there is no automatic migration or reset.

## Storage and resource contract

The SQLite store holds immutable AES-256-GCM pages and an authenticated directory. Encryption binds the profile, account, chain, protocol, deployment and compatibility binding. Each published directory binds the complete current and retained page set by ID, ciphertext digest and size. Startup streams and authenticates that full set before returning a usable store. Added, missing, modified or replayed individual rows refuse restoration. A complete old database can still be replayed: an external epoch and recovery policy remain necessary.

The resident directory uses prefix-compressed boundaries on disk; data is decoded one page at a time. Pages target 64 KiB, with a bounded larger page for a single value up to 1 MiB. Current history is limited to two million records, 1 GiB of plaintext and 32,768 pages. The encrypted directory is capped at 8 MiB and decoded separator keys at 16 MiB. SQLite uses a 4 GiB database-file ceiling, a 4 MiB page cache, no mmap, exclusive locking, DELETE journaling, `secure_delete`, `trusted_schema = OFF`, full synchronization and macOS `fullfsync`. The rollback journal is additional disk usage; 4 GiB is not a total filesystem footprint promise.

Each atomic publication bounds input and new page ciphertext separately at 32 MiB, and new plus deleted page bytes at 128 MiB, with separately bounded directory overhead. Compaction observes the remaining write budget. Garbage collection may defer excess retired pages; they remain authenticated, and reopening authenticates them before bounded collection. Whole-page range clearing does not materialize every deleted key.

At most two immutable cursors can pin prior revisions. Each has a five-minute idle timeout and a thirty-minute absolute lifetime. Snapshot-held superseded pages are limited to 96 MiB. Exceeding that limit **refuses the writer and revokes the session**, preserving the prior durable revision; it is not transparent backpressure. Regression tests pin both the refusal and successful collection after cursor release. Product scheduling and recovery must account for this policy.

The host's `nextMany` command returns up to 128 records, aiming for 512 KiB before one final bounded row, within the existing 2 MiB message limit. Iterator limits count rows delivered to the caller. Seeking discards prefetched rows without consuming the remaining allowance. Malformed replies, stale contexts and corruption still revoke capabilities. The existing exclusive tree transaction policy remains: concurrent wallet/scanner scheduling is a subsequent qualification task.

## Measured evidence

All reports below include source hashes and use public synthetic fixtures:

- [55 real-engine Node cases](qualification/railgun-paged-tree-2026-10-02.json) pass the tree transaction, SQLite fault, process interruption, frontier and replay matrix on the paged format.
- [13 Electron supervisor cases](qualification/railgun-paged-electron-2026-10-02.json) pass lifecycle, lock, restoration, memory and direct-egress refusal checks.
- [10 actual Electron tree runs](qualification/railgun-paged-electron-tree-2026-10-02.json) create 1,024 leaves, extend to 2,048, retain the old tree after lock or death during staging, and recover 4,096 leaves after death following an acknowledged commit. Main observes the explicit post-stage/post-commit markers and requires the expected SIGKILL exit. Fresh child processes independently reduce all synthetic leaves and compare the resulting root with the authenticated host store. Frontier status remains `persisted-unverified`, since synthetic consistency is not a chain anchor. The largest recorded frame is 695,364 bytes; cold iteration over 4,096 leaves uses 33 `nextMany` calls. All 90 direct-egress canaries refuse access, with zero operation attempts.
- [The 70,000-leaf volume run](qualification/railgun-paged-volume-2026-10-02.json) retains 210,032 records / 92,553,347 plaintext bytes in 1,449 pages, with a 208,191-byte directory and 99.24% page fill. The database file is 95,428,608 bytes. Maximum observed write/open/clear durations are 179.466 / 188.877 / 578.591 ms. This is a same-process synthetic measurement with checkpoint database reopenings, not a cold Electron lifecycle or live chain scan. Its 707,854,336-byte final RSS includes the engine and reference calculations; it is not store-only memory usage.

The measured synchronous maintenance stalls require moving storage work off the main event loop before product use. Capacity tests do not establish performance at the advertised maximum limits, on other platforms, or during a live scan.

Wallet decryption, nullifier history, note reservations, POI/TXID coverage and current Kohaku balance/notes semantics remain open.
