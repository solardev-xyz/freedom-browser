# PPv2 funded Sepolia lifecycle

All seven planned live transactions succeeded: two registrations, two native deposits, one relayed withdrawal and two emergency exits. All public submissions and the finalized relay are resolved. Fresh processes recovered the first deposit and withdrawal change. The final fresh process observed finalized block 11823409, both exited notes terminal, the original input spent and zero active notes. The bounded native lifecycle is complete. Production remains disabled.

This continues the [funding readiness report](ppv2-funding-readiness-2026-10-01.md). The test deliberately returns withdrawals to the public funding owner and selects direct HTTPS for the relayer. Owner/protocol RPC and ASP traffic use managed Arti/Tor. It qualifies protocol behavior, not transaction unlinkability or complete transport privacy. Chain observations remain explicitly unverified RPC evidence.

## Live interoperability fix

The first withdrawal preparation stopped before creating a relay journal record. A fresh process confirmed no relay attempt, an unchanged public balance and the original active note. Inspection showed that the live service returns the fee commitment's recipient checksummed while the wallet stores the same address in lowercase. That JSON field is unsigned; the signed routing data binds the same 20-byte address. The host's strict string comparison rejected this equivalent address.

Commit `17e65487` validates the recipient as a complete 20-byte hex address before comparing it case-insensitively. The relay request body is forwarded unchanged. Exact routing data, native gas value, fee, amount, domain, signer, proof, root, expiry and journal-before-send checks remain unchanged. Different addresses and malformed/non-string values remain refused. The service also omits `extraGas` from its raw quote; the SDK already defaults that field to false and serializes the complete nine-key handoff. No host schema relaxation was needed or retained.

The exact live-shaped quote fixture failed on the prior code and passed with the fix. Three affected direct-mode/controller Electron lifecycles passed after the change. The focused relay handoff, reconciliation and session suites passed (116 tests). The full unit suite passed as two exit-zero commands: 6,653 tests / 33 skipped across 315 suites, plus six OpenLV tests in isolation. The combined runner previously emitted late websocket logs from the unchanged OpenLV teardown; this is not a claim that that combined command exited cleanly. Lint passed. Claude independently reviewed the diagnosis, final diff and regression evidence before live continuation.

## Confirmed pending-exit state gap

The separate-note exit receipt succeeded and owner accounting matched exactly, but a fresh SDK status still called the exited 0.005 ETH note `active`. Static inspection of the pinned runtime explains the discrepancy: chain-observed ragequits become terminal `EXITED` only at or below the finalized status head. Before that boundary the SDK defers the event and retains its scan position. Its own execution path, or its explicit `markNotesExited` hook, sets provisional `EXIT_PENDING`; our reviewed external public handoff does neither.

The stale active state persisted for **at least ten minutes after explicit public resolution**: resolution was recorded at 17:38:45.791 UTC, while a fresh invocation starting at 17:49:05.380 still returned active. The actual note read happened after that invocation start. A subsequent fresh run observed finalized block 11823346: the separate exit at 11823319 was now exited, while the change exit at 11823378 remained active. That intermediate split is retained in the public JSON; it demonstrates the finality boundary without claiming independently verified chain state.

**Post-run follow-up:** [Host exit reservations](ppv2-exit-reservations-2026-10-01.md) now protect new attempts; the paragraphs below describe the funded-run baseline and the remaining recovery acceptance requirements.

This is a **product/release blocker for spendable-state correctness**, not evidence that the exit failed. After public resolution at twelve confirmations, the current host can still expose that note as active until finality. A second exit would fail simulation, but a relay withdrawal can reach a needless handoff/reservation before the relayer rejects the already-consumed nullifier. Later reconciliation may recover that needless attempt as an exit, but the extra relay request has already disclosed a link; the reservation must reject it before handoff. Do not use a successfully exited note again merely because its SDK status remains active.

The public journal currently stores only an operation kind and a transaction-intent digest; it does **not** retain the note commitment needed for a durable per-note exit reservation. Fix this deliberately: authenticated note-to-exit metadata written before handoff, restart/uncertain-delivery recovery, a provisional presentation/spend guard, and canonical/finalized resolution that can safely handle reorgs and failed transactions. A successful receipt must not directly set terminal `EXITED`. A generic pre-relay spent-nullifier query is not a substitute: it discloses a previously private nullifier to the RPC provider and needs its own privacy review. Test send-response loss, crash/restart, receipt before finality, reorg and failed/replaced outcomes. No SDK cache patch, journal format migration or runtime change was made during the funded run.

The reviewed follow-up constraints are:

1. Store note-to-exit metadata atomically with the pre-broadcast journal record. Derive it from the locally verified prepared ragequit, and authenticate it with the existing profile/account/deployment scope. A crash before transport still leaves a reservation; a missing response never releases it.
2. Apply a host-owned reservation to balance, note presentation and all preparation/submission paths before consulting the SDK's active status. An unresolved or included exit remains reserved even after generic public-transaction resolution. A reorg restores uncertainty, not spend permission. Release after failure needs matching finalized evidence and explicit review; a twelve-confirmation reverted receipt alone is insufficient. Nonce-consumed evidence does not establish which transaction executed.
3. Replay the SDK's provisional `markNotesExited` hook idempotently for supported source states, retaining the host reservation when the note is pending/inactive or the hook cannot run. `EXIT_PENDING`/`EXITED` must not be passed through a hook that accepts only active/rejected notes. Never invent an inclusion block. SDK cache rebuild must not lose the host reservation.
4. Keep old `{ kind, digest }` intents readable without silently attaching guessed commitments. A legacy recovery path can fetch the already-public transaction by its recorded hash, reconstruct its signed serialization and require the exact recorded hash plus recovered owner/nonce/chain/target. For retained live records, also recompute the exact stored intent digest before decoding the exit commitment. Archived public tombstones omit that digest, so authenticated recovery must rely on exact signed-transaction hash/sender reconstruction rather than pretend the digest was retained. Store a separately reviewed authenticated annotation; never infer identity from amount, ordering or the only visible note. Missing/mismatching recovery evidence blocks dependent spends. Archived/finalized public records do not prove that a rebuilt SDK cache applied the exit; preserve the binding through retention too.
5. Qualify crash-before-send, lost response, inclusion before finality, restart/cache rebuild, pending-note exit, reverted/replaced outcomes, reorg after review, ambiguous legacy history and archival behavior. An attempted withdrawal of the reserved note must be refused before relay journaling/network handoff, with no pre-spend nullifier query.

These are implementation requirements for the next slice, not functionality delivered by this experiment. The final exit selected only the distinct change note bound to the resolved relay's output. A status at finalized block 11823377 still correctly retained that later note as active; the final run at 11823409 recognized both exits. All six public records and the single relay record remained resolved, with no additional sends. The private status and journal reports preserve that binding; public evidence omits those identifiers.

## Follow-up engineering

- Close the pending-exit state gap above before exposing any spendable balance or withdrawal action to users. This takes priority over adding more protocol operations.
- Bound and expose SDK session-open progress. Registered-owner discovery currently scans auth events across approximately 179 serial history windows on every fresh session. The topic-only keystore scan currently uses the owner context because the SDK marks the keystore as a public contract. Consider routing account-independent log reads through the protocol context while retaining owner-keyed calls on the owner context. Real starts take minutes and transient Tor errors can stop them before preparation. A qualified incremental checkpoint must retain block-hash/reorg validation; do not silently assume cached identity is current. Consider a suitable contract view if the supported upstream API provides one.
- Preserve sanitized stage/transport error codes and an overall session-open deadline. After a reconciliation refusal, record the observation revision, scan checkpoint and finalized anchor so finality waits can be distinguished from failed reads without another full session. Current generic session errors obscure whether identity discovery or another read failed. Retry UX must distinguish a pre-send refusal from an uncertain durable handoff.
- Complete supported upstream revision/derivation identity, audit/deployment provenance, portable backup, whole-profile rollback, platform/egress and product approval/UX gates before release. Tor-compatible relaying remains unqualified.
- Make qualification readiness operation-specific: an ASP outage currently blocks the harness even for ragequit, although emergency exit must remain possible without ASP approval. Qualify the complete exit path during an ASP outage and retain all chain, deployment, verifier, proof and owner checks. Do not change these gates halfway through a funded run.
- Expand the exact live quote shape to Tor-mode fixtures and use a lettered synthetic recipient in preflight; the newly qualified direct/controller fixtures catch casing, but the other fixtures still use lowercase addresses and explicit `extraGas`. Record accepted relay summary fields and quote time remaining at review, and remove the undefined explorer URL from reports.
- Measure owner-route failure rates and session latency before claiming reliable live operation through Tor.
- Live ERC-20, private transfer, full/zero-change withdrawals, larger circuits and coordinated uncertain-delivery injection remain separate tests. Controlled fixtures already cover broader recovery behavior; this live native experiment does not replace those remaining gates.
