## Resulting behavior

| Finding | Change |
| --- | --- |
| An unresolved relay could permanently block even emergency exit | An explicitly reviewed ragequit can compete for the same nullifier. Matching owner, input commitment, nullifier, asset, value and receipt evidence is required before a separate reconciliation review releases the relay reservation. A relayer can still win the race; an HTTP error never proves cancellation. |
| A public transaction never seen by the provider could reserve its nonce indefinitely | Explicit review may accept a finalized account nonce beyond the recorded nonce, anchored to a stable block. Status is `nonce-consumed`: it does **not** claim the original transaction succeeded or identify a replacement. A still-pending transaction needs a replacement outside this experimental session; this branch supplies no automatic replacement/resend. |
| Depositing under another immutable nullifying key could strand notes | Derive the expected registration from the pinned candidate/account and compare calldata plus chain reads before deposit and again after approval. A different nullifying key refuses session opening. A viewing-key-only change leaves recovery available, blocks deposits, and exposes a separately reviewed repair preparation marked as replacing an existing viewing key. |
| Valid deposit proofs alone did not demonstrate owner recovery | Decrypt the local recipient announcement and recompute the commitment; require the expected owner, amount and asset. ASP announcement semantics remain an upstream SDK assumption. |
| Quote expiry during the final eligibility check could leave an avoidable uncertain attempt | Reserve only after a bounded review and recheck, with a 15-second delivery margin. Preparation and submission entry enforce the margin too. Timed-out rechecks receive cancellation and cannot write late reconciliation results. Delivery is still uncertain after the durable reservation. |
| RPC outages erased reviewed history | Missing/index-pruned/error responses block the current action without erasing reviewed inclusion. Positive canonical hash changes revoke permission. Already reviewed history uses compact exact-height/hash checks, with bounded concurrency and per-operation transport release. |
| Owner and private reads shared transport contexts | Keystore/ERC-20 owner reads use the public owner's context; relay settlement checks use the attempt's private operation context. Tor endpoint replacement revokes the session and releases its lease. Failed chain checks may be retried by a later explicit read. |
| Password changes could disable vault auto-lock | Password verification/re-encryption no longer creates or mutates an unlocked session; the original deadline and cancellation signal remain in force. |
| Electron could clone unrelated pooled-buffer bytes | Artifact buffers own their full allocation. The process boundary rejects partial/pooled views and bare backing stores before fork and again before IPC. Real Electron qualification checks each received artifact's exact backing size. Shape checks do not prove allocation provenance; main owns all job inputs. |
| A moved profile or missing journal could look like an empty history | A vault-authenticated profile inventory covers SDK state and both journals. Moved profiles, missing listed stores, corrupt/foreign inventories, and legacy stores without an inventory fail closed. Files enter the inventory only after durable write or successful authentication, allowing recovery from an interrupted inventory update. |
| Worker and network tripwires had gaps | Worker results require an explicit validator and a 1 MiB serialized cap. DNS Resolver/reverse and direct dgram constructor paths receive the same process tripwires, including nested-worker checks. These are defense in depth, not an OS sandbox. |
| Recovery page and test-harness failures | Settlement discovery starts 1,000 blocks before the lesser of the observed latest/finalized heights, bounded by the configured deployment block, with durable checkpoints and an explicit smaller-page option (`maxBlocks`, 1–5000), no hidden retry. Electron fixtures await readiness and bound shutdown of their own child. Negative quote tests assert the intended refusal and absence of sends/reservations. |

The new inventory remains in `src/main/wallet/` because it owns privacy persistence, alongside the encrypted stores. Main, identity, network and renderer responsibilities are unchanged; no new UI/IPC route or application dependency is introduced.

## Scope and limitations that remain

- **Production is disabled.** The development gate is unavailable in packaged builds; controlled tests inject only synthetic, main-process fixture services. Ordinary wallet sends remain outside the PPv2 session's reservation gate and retain their existing network path. They may consume a public account nonce.
- **Trust is explicit.** Block hashes, finality, nonces, roots, receipts and ASP state still come from unverified remote evidence. Compact checks bind the exact reviewed height/hash; missing evidence blocks, and contradictory evidence revokes. This does not establish a light-client proof.
- **Privacy is scoped.** Separate SOCKS tokens/pools prevent context sharing, not timing correlation. Owner reads during proving and historical block queries around a new spend remain correlatable by the same RPC operator. Bounded parallel checks can make that timing pattern clearer. A context may legitimately use multiple Tor circuits; requiring exactly one circuit would be an incorrect acceptance test.
- **Recovery is not portable yet.** A moved profile is deliberately blocked pending reviewed migration. Legacy stores without inventories and legacy relay records without sufficient settlement/owner metadata require recovery design; they are never silently discarded or released. Deleting or rolling back the entire profile, including its inventory, is not detectable with a colocated marker. Whole-profile anti-rollback needs an independent trust root. Encrypted temporary files can remain after interrupted writes; bounded cleanup remains work.
- **Coverage is narrow.** Withdrawals are single-input/single-output with positive private change. Full-value withdrawal with zero change, private transfers, other circuit shapes, asset behaviors and hardware/remote signers require separate qualification. The positive-change condition predates this review and is consistently enforced at witness and relay boundaries.
- **Capacity and performance are bounded.** Journals retain at most 64 attempts, and no retention/compaction policy is shipped. Smaller explicit pages handle ordinary provider range limits; a single block exceeding the log/body cap still cannot be processed. Latest/finalized scan anchors are themselves unverified; a lying RPC can also hide logs. The SDK's separate general log-scanning policy is not made unbounded. Controlled quote tests do not establish real Tor latency or guarantee relayer delivery. Some older non-quote negative fixtures still accept a generic operation error; their refusal-specific diagnostic coverage remains narrower than the new signed/short-quote checks.
- **Provenance and verification are bounded.** SDK `fe0244e3f14110efd83db02c60c96517dea9cd5a` and Kohaku `6fdc248b3d28942d9aaa35c49c1ac76dab89dc0e` remain the qualification pins. Candidate strings are not code authentication; the scratch ASAR is not a production distribution chain. Session proof production and verification execute in the same owned process with pinned artifacts. A separate verifier process is exercised by the standalone relay fixture; that is not the session's independent-verifier architecture. JavaScript secrets cannot be guaranteed erased.
- **Upstream/live gates remain.** Final production derivation identity, audited source/setup and matching deployed contracts/verifiers, ASP and relayer configuration/signers, maintained package distribution, live Sepolia recovery and supported-platform/OS egress qualification must precede activation. A newer upstream revision must be evaluated deliberately rather than silently replacing this pin.
